## Story

As a **operador/gestor da rádio**, I want **cadastrar a escala semanal dos
locutores (quem está no ar em cada faixa de horário de cada dia da semana)**, so
that **a operação saiba a qualquer instante quem é o locutor de plantão e a grade
humana fique registrada junto do resto da automação**.

## Acceptance Criteria

1. Domínio `staffschedule` puro (zero deps externas, sem clock, sem persistência):
   value object `Shift{ID, AnnouncerID, AnnouncerName, Weekday, StartMin, EndMin}`
   com `Weekday` = `time.Weekday` (0=domingo … 6=sábado) e `StartMin`/`EndMin` em
   minutos desde a meia-noite (0…1440). Cobertura 100%.
2. `Shift.Validate()` rejeita: id vazio (`ErrEmptyID`), locutor vazio
   (`ErrEmptyAnnouncer`), weekday fora de 0..6 (`ErrBadWeekday`), intervalo
   inválido — fora de 0..1440 ou start≥end (`ErrBadRange`).
3. `Roster` agrega turnos validados: `BuildRoster([]Shift)` valida cada turno e
   **detecta sobreposição** no mesmo dia (`ErrOverlap`) — só um locutor no ar por
   vez. `Roster.OnAir(weekday, minute)` retorna o turno vigente (se houver);
   `Roster.Shifts()` retorna ordenado por (weekday, start); `Roster.ForWeekday(w)`
   filtra por dia.
4. Portas: outbound `StaffScheduleRepo{ Save, Get, Delete, List }` +
   `ErrShiftNotFound`; inbound `StaffScheduleService{ AddShift, RemoveShift,
   Roster, OnAir }`. `AddShift` gera id determinístico (clock + contador), valida
   o turno novo contra os existentes (rejeita sobreposição com `ErrOverlap`) e
   persiste. `OnAir` usa o clock injetado.
5. Persistência: repos memory + sqlite + postgres (trio, espelhando `requests`).
   sqlite entra no gate de cobertura (round-trip + erro de decode + DB fechado);
   postgres é integration-tier (só compila). Tabela `staff_shifts` em `schema.sql`
   + migração numerada.
6. REST sob `/api/v1`: `GET /staff/shifts` (lista), `POST /staff/shifts`
   (cria — body snake_case), `DELETE /staff/shifts/{id}` (remove),
   `GET /staff/onair` (locutor de plantão agora, ou 204 se ninguém). Mapeamento de
   erro: validação→422, `ErrOverlap`→409, `ErrShiftNotFound`→404. Handlers/rotas
   protegidos por Option `WithStaffSchedule` (rota ausente → 404). Cobertura ≥90%.
7. UI: painel "🗂 Escala" no OperacionalScreen — lista turnos por dia, formulário
   de cadastro (locutor, dia, início/fim), remoção, e destaque de quem está no ar
   agora. Tipos/fetch em `lib/api.ts`, hook `useStaffSchedule`, componente único
   `StaffSchedulePanel.tsx`. `pnpm build` verde.

## Dev Notes

**Contexto puro.** Escala de trabalho é grade *humana* (quem locuta quando), não
grade *musical*. Não toca áudio, não entra no bus de playout, não tem relação com
o invariante dois-motores — é metadado organizacional. Modelado como bounded
context stateful próprio (igual `requests`), com trio de repos.

**Minutos desde meia-noite.** `StartMin`/`EndMin` são inteiros 0..1440 — evita
fuso, DST e parsing de string no domínio. UI converte `HH:MM`↔minutos. Intervalo
半-aberto `[start, end)`: `OnAir` casa `minute >= start && minute < end`.

**Overlap = invariante de negócio.** Só um locutor no ar por vez, então dois
turnos no mesmo weekday não podem se intersectar. `Roster.BuildRoster` ordena por
(weekday, start) e detecta interseção de intervalos adjacentes. `AddShift`
reconstrói o roster com o turno candidato para validar antes de salvar.

**Id determinístico.** Igual `RequestService`: `staff-<unixnano>-<seq>` sob mutex,
para testes reprodutíveis com fake clock.

**Persistência (trio requests).** memory = `sync.RWMutex`+map+sort; sqlite = blob
JSON + colunas denormalizadas (`announcer_id`, `weekday`) com `ON CONFLICT(id) DO
UPDATE`, `scanShift(rowScanner)`; postgres espelha (só compila). Tabela
`staff_shifts(id TEXT PK, announcer_id TEXT, weekday INT, data TEXT)`.
