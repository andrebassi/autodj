# Story 9.4 — Modo single-user (1:1, sem tela de login)

## Status

Done

## Executor Assignment

- **executor**: @dev
- **quality_gate**: @architect
- **quality_gate_tools**: `task cover` (app ≥90%), `go build ./...`, `pnpm build`

## Story

As a **operador de uma rádio caseira 1:1**, I want **abrir o AutoDJ e cair direto no
console, sem passar por tela de login**, so that **o sistema de uso pessoal (um único
operador) não me obrigue a autenticar toda vez, mantendo o RBAC intacto para o dia em
que virar multiusuário**.

## Acceptance Criteria

1. Existe um decorator `app.SingleUserAuth` que embrulha um `inbound.AuthService` e um
   operador fixo (o admin semeado). Com **token vazio**, `Me` e `Authorize` resolvem
   para esse operador (sem 401); com **token presente**, tentam o serviço interno e
   só honram a identidade se o token for **válido** — token **stale/inválido** (sobra
   de sessão multiusuário no `localStorage`) **cai de volta para o operador**, nunca
   401/tela de login (single-user 1:1 de verdade, independente de estado do client).
   Trocar de volta para multiusuário não exige mudança de código.
2. `Login`, `ListUsers`, `CreateUser`, `UpdateUser`, `DeleteUser` **delegam intactos**
   ao serviço interno — gestão de usuários continua funcionando (repo real).
3. `SingleUserAuth` satisfaz `inbound.AuthService` (compile-time assert) e tem teste
   próprio no `app/` cobrindo os dois caminhos (token vazio → operador; token presente
   → delega) e os delegates, mantendo o pacote `app` ≥90%.
4. `cmd/serverkit` liga o modo por env **`AUTODJ_SINGLE_USER`** (default **ligado** para
   uso caseiro; `=0`/`false` volta ao multiusuário real). Quando ligado, o operador é o
   admin (semeado ou lido do repo por nome) e o `AuthService` exposto às rotas é o
   decorator.
5. O frontend não mostra tela de login no modo single-user: `useAuth` tenta `fetchMe`
   no boot **mesmo sem token** — o backend devolve o operador → console renderiza
   direto. Se `fetchMe` der 401 (modo multiusuário), a `LoginScreen` aparece como antes.
6. Invariante dois-motores (`spotify ⇒ mixable=false`) e persistência (SQLite por
   usuário) **inalterados** — esta story só afeta autenticação/gate de UI.
7. Gate de cobertura verde (`app` ≥90%), `go build ./...` compila, `pnpm build` compila.

## Dev Notes

- **Por que decorator e não novo serviço**: o RBAC (Story 7.3) e a gestão de usuários
  continuam valendo; o modo caseiro só dispensa a autenticação da sessão. Embrulhar o
  `AuthService` real preserva `Login`/CRUD e mantém o operador como um `identity.User`
  admin de verdade (permissões resolvidas pela matriz do domínio), então `Authorize`
  com token vazio passa em toda permissão sem caso especial por permissão.
- **Operador quando o seed é no-op**: `SeedAdmin` devolve user zero quando já há conta.
  O serverkit então lê o admin por nome no `userRepo` (`GetByName`) para ter a
  identidade do operador do decorator — nunca depende do retorno do seed.
- **Token vazio vs presente**: manter o caminho de token presente delegando ao interno
  deixa o modo multiusuário (env `=0`) 100% intacto e permite emitir/usar tokens reais
  mesmo com o decorator ligado (defense-in-depth; não usado pela UI caseira).
- **Front**: `fetchMe` já manda `authHeader()` vazio quando não há token, então o GET
  `/auth/me` sem `Authorization` chega ao backend como bearer `""` — exatamente o
  caminho que o decorator resolve para o operador. Nenhuma mudança em `lib/api.ts`.
- **serverkit é integration-tier**: fora do gate unitário — a lógica testável vive no
  decorator em `app/` (coberto), não no wiring.

### Testing

- `app/single_user_auth_test.go`: token vazio → operador em `Me`/`Authorize`; token
  presente → delega (fake inner registra chamada); `Authorize` nega permissão que o
  operador não tem (operador não-admin); delegates (`Login`/`ListUsers`/CRUD) chamam o
  interno. Fakes locais implementando `inbound.AuthService`.
