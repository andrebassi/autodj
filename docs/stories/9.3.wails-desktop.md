## Story

As a **operador de rádio caseira**, I want **rodar o AutoDJ como um aplicativo de
desktop (janela nativa) em vez de abrir o navegador**, so that **eu tenha a estação
como um programa que abre com um clique, no mesmo domínio Go, sem depender de um
navegador aberto nem de servidor remoto**.

## Acceptance Criteria

1. O wiring do backend (repos, engine, serviços, seeds, rotas REST + WebSocket +
   UI estática) é extraído para um pacote reutilizável `cmd/serverkit`, exposto como
   `Build(ctx) (http.Handler, func(), error)` — o `func()` desliga tudo (fecha DB,
   para análise). `cmd/server` passa a ser fino: só sinal + `Build` + `http.Server`.
2. O comportamento de `cmd/server` é idêntico ao anterior (mesmas envs, mesma
   precedência de repo/engine, mesmos seeds, mesma porta `PORT`).
3. `cmd/desktop` (build tag `//go:build desktop`) empacota a mesma UI + o mesmo
   domínio Go numa janela Wails: sobe o handler de `serverkit.Build` num listener
   local `127.0.0.1` e a janela Wails serve tudo via `AssetServer.Handler`
   (reverse-proxy) — sem duplicar wiring, sem segundo binário de backend.
4. O código Wails fica **inteiramente atrás do build tag `desktop`** — `go build ./...`,
   `go test ./...` e o gate de cobertura **não** tentam compilar Wails nem exigem a
   dependência nativa (webkit). O caminho unitário/CI permanece limpo.
5. `wails.json` na raiz declara o frontend (`web/`, `pnpm build`); o Taskfile ganha
   `desktop:dev` e `desktop:build` (buildam `web/out` e compilam com `-tags desktop`).
6. A persistência do desktop é a mesma do uso caseiro: SQLite por usuário
   (`~/.autodj/library.db`), sem daemon — a biblioteca sobrevive a reinícios.
7. Gate de cobertura verde (nada novo entra em pacote coberto — `cmd/*` é
   integration-tier), `go build ./cmd/server` compila, `pnpm build` compila.

## Dev Notes

**Por que reverse-proxy e não embed Wails.** O frontend fala REST relativo
(`apiBase()` vazio ⇒ `/api/...` na mesma origem). Basta a origem servir `/api`,
`/ws` e os estáticos. `serverkit.Build` já devolve esse handler completo (API +
WS + `web/out` em disco). O desktop sobe esse handler num `127.0.0.1:0` e a janela
Wails proxya tudo via `AssetServer.Handler` — origem única, sem duplicar wiring,
sem `//go:embed web/out` (que não atravessa `..` a partir de `cmd/desktop`).

**Build tag.** Toda a superfície Wails (import `github.com/wailsapp/wails/v2`,
webkit nativo) vive em arquivos `//go:build desktop`. O gate roda `go test ./...`
sem o tag ⇒ o pacote `cmd/desktop` é excluído da compilação; nenhum dep Wails entra
no `go.mod` do caminho unitário. Compilar o desktop de verdade:
`cd web && pnpm build && go build -tags desktop -o bin/autodj-desktop ./cmd/desktop`
(a máquina precisa do toolchain Wails/webkit; `wails dev -tags desktop` para hot-reload).

**serverkit = integration-tier.** Fica sob `cmd/`, já excluído pelo
`coverage-gate.sh` (`EXCLUDE_RE` casa `autodj/cmd/`). É wiring puro (sem lógica de
domínio) — coberto pelos runs end-to-end, não por unit. Nenhum pacote coberto muda,
então o gate segue verde.

**Invariante dois-motores.** Desktop é só empacotamento (janela + processo); não
toca áudio nem no bus de playout. O invariante `spotify ⇒ mixable=false` continua
imposto nas 4 camadas de sempre (domínio/fila/engine/banco), intacto.

### Testing

Sem teste unitário novo: a story é infra/empacotamento (como 1.1/1.5). `cmd/serverkit`
e `cmd/desktop` são integration-tier (fora do gate). Verificação: `task cover` verde
(nenhum pacote coberto alterado), `go build ./cmd/server` compila o caminho fino, e
`pnpm build` compila o frontend que a janela serve.
