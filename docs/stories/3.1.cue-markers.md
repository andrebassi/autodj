## Story

**As a** operador da rádio caseira,
**I want** marcar pontos de cue numa faixa PCM — start, intro, refrão, carimbo, mixin, mixout, end — com posição em ms e rótulo,
**so that** o scheduler e o deck saibam onde a música "entra"/"sai" para mixar fino (crossfade/ducking) sem cortar seco, e Spotify (DRM) fica de fora porque não há PCM para marcar.

> **Contexto de escopo.** Épico 3 = markers + editor waveform + mixagem fina. Esta primeira story entrega o **modelo de domínio + persistência + API** dos marcadores — a fundação que o editor de waveform (3.2) e a mixagem por tipo (3.3) consomem. Sem UI de edição ainda (fica em 3.2): aqui os marcadores nascem no domínio, viajam junto da `Track` (mesmo padrão de `WaveformRef`/`BPM`), persistem nos três repos (memory/sqlite/postgres) e são lidos/gravados via REST. Invariante dois-motores preservado: **marcadores só existem para fontes PCM** — `SetMarkers` recusa não-PCM (`ErrMarkersNotPCM`), coerente com a matriz de capacidade (Marker/Beatgrid/waveform só PCM).

## Acceptance Criteria

1. **Value object `Marker` no domínio.** `library.MarkerKind` (enum: `start`, `intro`, `hook`, `stamp`, `mixin`, `mixout`, `end`) com `Valid()`; `library.Marker{Kind, PosMs, Label}`. Identificadores em inglês; rótulos pt-BR ficam na camada de apresentação/UI (fora desta story).
2. **`Track.SetMarkers([]Marker) error`.** Recusa fonte não-PCM (`ErrMarkersNotPCM`); rejeita kind inválido (`ErrBadMarkerKind`); rejeita posição fora de `[0, Duration]` (`ErrMarkerOutOfRange`); rejeita duplicata de kind singleton — `start`/`end`/`intro`/`mixin`/`mixout` (um por faixa) — com `ErrDuplicateMarker` (`stamp`/`hook` podem repetir); rejeita `start > end` e `mixin > mixout` (`ErrMarkerOrder`); **ordena por `PosMs`** (estável) e grava. Slice vazio limpa os marcadores. `Track.Markers []Marker` como campo derivado (não setar direto — usar `SetMarkers`). Domínio 100%.
3. **Persistência round-trip nos três repos.** `memory` (deep-copy do slice — sem aliasing entre chamadas), `sqlite` (coluna `markers TEXT` JSON, com migração idempotente `ALTER TABLE ADD COLUMN` para bases já existentes) e `postgres` (coluna `markers JSONB`, migração `003`). `Upsert`/`Get`/`List` preservam os marcadores. Sem quebrar o CHECK `spotify_never_mixable`.
4. **Serviço de aplicação `SetMarkers`.** `LibraryService.SetMarkers(ctx, id, []Marker) (*Track, error)`: busca a faixa (`ErrTrackNotFound` se ausente), aplica no domínio (propaga erros de validação), re-faz `Upsert`, devolve a faixa atualizada. Não toca metadata/flags.
5. **API REST.** `PUT /api/v1/library/tracks/{id}/markers` recebe `{markers:[{kind,pos_ms,label}]}`, chama o serviço, devolve o `trackDTO` atualizado. `trackDTO` ganha `markers []markerDTO` (`kind,pos_ms,label`). Erros mapeados: não-encontrado→404, não-PCM/kind inválido/fora de faixa/duplicata/ordem→422.
6. `GOWORK=off go test ./... -cover` verde: domínio 100% (todos os ramos de `SetMarkers` + `MarkerKind.Valid`), `app`/`httpapi`/`memory`/`sqlite` ≥90%. Gate `./scripts/coverage-gate.sh` passa.

## Dev Notes

- **Por que marcadores ficam na `Track`.** São intrínsecos à faixa (como `BPM`/`WaveformRef`), poucos por faixa (≤~10), e sempre lidos junto dela. Guardar como coluna JSON evita uma tabela/junção e mantém a interface `TrackRepo` intacta — `SetMarkers` = `Get`+domínio+`Upsert`, sem novo método de porta. Se no futuro virarem muitos/consultáveis, migra para tabela própria; hoje seria over-engineering.
- **Invariante dois-motores.** `SetMarkers` recusa não-PCM com `ErrMarkersNotPCM` — Spotify nunca ganha cue points, coerente com a matriz (Marker/Beatgrid/waveform só PCM) e com o pipeline de análise (3ª story do Épico 2). O CHECK de banco de mixabilidade continua intacto; marcadores não afetam `mixable`.
- **Kinds singleton vs repetíveis.** `start`/`end`/`intro`/`mixin`/`mixout` são únicos por faixa (fazem sentido só uma vez — onde a música começa/termina, onde entra/sai na mix). `stamp` (carimbo/ID da emissora) e `hook` (refrão) podem repetir. Ordem checada: `start ≤ end`, `mixin ≤ mixout` — o resto é livre; ordena por posição para o editor renderizar em sequência.
- **Migração idempotente (sqlite).** O schema embutido usa `CREATE TABLE IF NOT EXISTS`, então bases já criadas não ganham a coluna nova só por reaplicar o schema. `Open` chama `ensureMarkersColumn`: sonda com `SELECT markers FROM tracks LIMIT 0` — se a coluna existe, no-op; senão roda `ALTER TABLE tracks ADD COLUMN markers TEXT NOT NULL DEFAULT '[]'`. Seguro em base nova (schema já a cria) e antiga.
- **Serialização.** JSON `[]Marker` como string no sqlite / `jsonb` no postgres. Slice nil grava `[]` (não `null`) para round-trip estável; `Get`/`List` desserializam de volta. A ordenação por posição acontece no domínio (`SetMarkers`), então o que persiste já está ordenado.
- **Sem UI aqui.** O editor de waveform com arrasto de marcadores é a 3.2 — esta story só expõe os dados (DTO + PUT). Frontend não muda; nada de lista hardcoded. Regra "Frontend SEMPRE em componentes" vale para 3.2, quando o editor entrar.
