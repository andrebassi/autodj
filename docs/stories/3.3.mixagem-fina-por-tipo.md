## Story

**As a** operador da rádio caseira,
**I want** configurar a mixagem fina por tipo de mídia — fade in/out separado para músicas, vinhetas e comerciais, ducking na sobreposição e na fala, corte de silêncio e normalização de volume — e que essa configuração persista,
**so that** a rádio encadeie os itens do jeito que eu quero (crossfade suave nas músicas, corte curto nas vinhetas) sem reconfigurar a cada boot, com a config valendo como fonte de verdade para o motor de playout.

> **Contexto de escopo.** Épico 3 = markers + editor waveform + mixagem fina. 3.1 entregou o modelo de marcadores; 3.2 o editor de waveform. Esta story (3.3) fecha o épico com a **configuração de mixagem por tipo**, promovendo o `MixConfig` — que até agora era só seed de UI no `domain/content` (servido em `/ui/operational`, sem persistir) — a um **value object de domínio `mixing.Settings` com `Validate()`**, persistido single-row nos três repos e lido/gravado via REST `GET/PUT /mix`. A UI (`MixConfigModal`) deixa de ser só visual: carrega do backend e salva de verdade. O default de fábrica fica no domínio (`mixing.Default()`); o seed do `content` continua existindo (fallback antes do fetch) e um teste de paridade garante que os dois não divergem.

## Acceptance Criteria

1. **Value object `mixing.Settings` no domínio.** Campos (ms/%): `MusicaIn/MusicaOut`, `VinhetaIn/VinhetaOut`, `ComercialIn/ComercialOut` (fades por tipo), `OverlapVol`, `TalkVol` (ducking), `TrimMusicas`, `TrimVinhetas` (corte de silêncio), `Normalize`, `NormalizeVol`. Tags JSON camelCase idênticas ao `content.MixConfig` (contrato de fio estável). `mixing.Default()` devolve a config de fábrica (MusicaIn 500 / MusicaOut 2000 / VinhetaIn 50 / VinhetaOut 1000 / ComercialIn 50 / ComercialOut 1000 / OverlapVol 30 / TalkVol 20 / TrimMusicas true / TrimVinhetas false / Normalize true / NormalizeVol 89). `Settings.Validate()`: fades em `[0, 30000]ms` (`ErrNegativeFade`/`ErrFadeTooLong`), percentuais em `[0,100]` (`ErrVolPercent`). Domínio 100%.
2. **Porta `outbound.MixSettingsRepo`.** `Get(ctx) (Settings, error)` devolve as settings gravadas ou `mixing.Default()` se nunca salvou; `Save(ctx, Settings) error` grava (single-row).
3. **Persistência single-row nos três repos.** `memory` (arranca em `Default()`, `Save` substitui), `sqlite` (tabela `mix_settings(id CHECK id=1, data JSON)`, blob JSON, `Get` sem linha → `Default()`), `postgres` (tabela `mix_settings` `jsonb`, migração `004`). `sqlite`/`postgres` compartilham o handle do `TrackRepo` via método `Mixing()`.
4. **Serviço de aplicação `MixService`.** `Get(ctx) (Settings, error)` delega ao repo; `Save(ctx, Settings) (Settings, error)` valida no domínio (propaga erro sem gravar), persiste, relê e devolve.
5. **API REST.** `GET /api/v1/mix` → `Settings` JSON; `PUT /api/v1/mix` recebe `Settings` JSON, valida/persiste, devolve a config atual. Validação falha → 422. Body inválido → 400.
6. **Frontend liga na API.** `web/app/lib/api.ts` ganha `fetchMix`/`saveMix`; hook `useMix` carrega/salva; `MixConfigModal` carrega do backend (fallback `EMPTY_OPERATIONAL.mix`) e o botão Salvar persiste via `PUT /mix` e fecha. Sem listas hardcoded; componente por arquivo.
7. `GOWORK=off go test ./... -cover` verde: domínio 100% (todos os ramos de `Validate` + `Default`), `app`/`httpapi`/`memory`/`sqlite`/`mixing` ≥90%. Gate `./scripts/coverage-gate.sh` passa. `pnpm build` do `web/` compila.

## Dev Notes

- **Contrato de fio:** `mixing.Settings` reusa os nomes camelCase de `content.MixConfig` — o mesmo JSON já consumido pelo `MixConfigModal`. `/mix` é a fonte persistida; `/ui/operational.mix` continua devolvendo o seed (default) como fallback pré-fetch. Teste de paridade impede drift entre os dois defaults.
- **Single-row:** id fixo `1` com CHECK; `Get` sem linha devolve `Default()` (nunca erro "vazio"). `Save` faz upsert. sqlite guarda blob JSON numa coluna `data TEXT`; postgres `jsonb`.
- **Invariante dois-motores:** mixagem é config global de playout (não por faixa), então não toca a matriz PCM/DRM — Spotify continua `mixable=false` e fora do bus; a config só molda como o motor local encadeia PCM.
- **Wiring engine (futuro):** os fades daqui alimentarão o `.liq` do Liquidsoap (crossfade a partir do MusicaOut) em épico posterior; esta story entrega domínio+persistência+API+UI. Sem tocar o hot-path de playout agora.

### Testing

- Domínio: table-driven cobrindo `Default` e cada ramo de `Validate` (fade negativo, fade > 30000, vol < 0, vol > 100, happy).
- `app`: fake repo; `Save` válido persiste e relê; `Save` inválido não grava e propaga; erro do repo propaga.
- `memory`/`sqlite`: round-trip (Save→Get) + `Get` inicial = `Default()`.
- `httpapi`: `GET /mix` (200 + corpo), `PUT /mix` ok (200), inválido (422), body ruim (400).
